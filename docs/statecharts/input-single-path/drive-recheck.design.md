## 설계

### Queue와 timer의 소유권

1. `src/services/discord/queue_io/input_owner/drive.rs:113-116`의 Held 처리와 `src/services/discord/queue_io/input_owner/drive.rs:184-205`의 no-grant/stalled 종료를 하나의 판정 루프로 연결한다. actor에서 `items`, `head_injection`, 현재 원본과 세대, grant blocker, 기존 due를 함께 읽는다. `front() == None`이어도 head·close/effort·retry wait에 가려진 일이 남을 수 있다. head가 실행권을 갖는 동안 정산 상태를 관찰한다. active/unknown head를 다시 보내거나 retained-only 원본을 재큐잉하는 경로는 추가하지 않는다.
2. 채널별 단일 drive task가 판정, monotonic timer, coalesced wake를 다룬다. 계속 막히면 1→2→5→10→10초 간격이다. 새 입력 및 turn boundary의 기존 wake는 `again`을 세우고 `Notify` permit을 남긴다. 대기 전에 notification을 등록하고 flag를 재확인한다. wake가 들어오면 즉시 판정하고 다음 기다림을 1초로 되돌린다. timer expiry는 wake reset을 일으키지 않는다. 현재 pass가 실행 중이면 기존 권리를 유지하고 끝난 직후 한 번 더 본다.
3. 기존 수락과 boot 채택이 drive를 시작한다. actor가 첫 work snapshot과 queue 활동 구독을 함께 넘긴다. queue commit은 empty/nonempty 및 현재 원본 세대의 변경만 알린다. 외부 cancel/clear/terminal commit가 빈 큐를 만들면 이 신호가 대기를 종료시킨다. actor 종료나 대체는 해당 세대의 task를 끝낸다. 빈 큐 판정과 새 수락이 겹치면 기존 running/again release·reacquire 순서로 wake를 넘긴다. transient read error는 빈 큐와 구별하고 actor가 살아 있는 pending episode에서만 retry한다.
4. 기존 `arm_deadline` 신호와 detached deadline sleep을 같은 lane에 통합한다. `min(next_recheck, exact_owner_due)` 하나만 기다린다. 기존 wall-clock due는 actor에서 현재 milestone과 시각을 확인한 뒤 소비한다. 빈 큐면 sleep을 drop하고 별도 TUI watch를 정확한 세대로 취소한다. 이미 실행 중인 bounded blocking probe는 결과를 폐기한다. 독립 restart/handoff journal 작업과 이미 청구된 영속 의무는 기존 lifecycle에서 정산한다. 빈 큐 판정은 채널의 입력 재판정 작업을 대상으로 한다.
5. TUI `held_watch`는 화면 회복을 먼저 감지할 수 있다. 같은 원본/사유/binding의 세대를 유지하고 새 probe로 교체하지 않는다. watch wake, turn boundary, 새 입력과 timer가 겹치면 같은 실행권에 합친다. 이전 watch의 결과는 세대와 현재 front가 모두 일치할 때만 wake를 보낸다. watch 생존이나 결과는 재판정의 진입 조건에 없다.

### 호스트 중립 판정과 실제 effect

루프는 기존 판정이 호스트에서 읽는 `Idle / Busy / Unknown`과 현재 readiness, source·execution 세대만 전달 조건으로 받는다. tmux·Herdr TUI의 입력은 turn presence, transcript와 hook 근거다. 사람·합성 origin의 기존 route 규칙은 그대로 적용한다. 현재 helper가 읽기와 publish/recover를 함께 수행하는 곳은 기존 판정의 관측 부분을 분리한다. 호스트별 선택은 기존 값을 읽는 경계에 둔다. scheduler·backoff·queue lifecycle은 호스트 종류를 입력으로 받지 않는다.

기존 pane capture, draft와 composer 검사는 허가된 정상 TUI handoff의 safety fence 및 기존 `held_watch`에 있다. timer가 호출하는 준비도 판정에는 화면 판독을 추가하지 않는다. 반복되는 reserve→rollback·receipt·DB 쓰기는 기존 pre-key guard를 효과 전에 한 번 소비하도록 경계를 정리한다. 기존 writer lease, NoKeyYet, exact owner와 epoch의 유효성은 첫 키까지 보존한다. 그 사이에 실행 권한이 바뀌면 drop하고 다음 pass가 지금의 근거를 읽는다. 이 경계를 동일 lock에서 지킬 수 없는 기존 leaf는 구현 레그에서 따로 손볼 대상이다.

화면에만 드러나는 조건에는 관측 한계가 있다. modal이 닫혀도 호스트가 같은 근거만 발행하면 timer는 그 차이를 관측할 수 없다. 기존 TUI watch가 그 회복을 빠르게 읽을 수 있다. 상태 차트 liveness는 호스트가 제공하는 전달 조건과 owner gate가 풀리는 경우를 검증한다. 허가된 정상 handoff는 기존 writer guard를 통과해야 한다. 화면 변화만 있는 상태에 대한 독립적인 10초 전달 보장은 이 호스트 계약만으로 성립하지 않는다.

영속 retry wait의 30~300초 정책과 never-started close authority는 `src/services/turn_orchestrator/queued_head/v2/retry_wait.rs:5-9,126-147`에 있다. timer는 Pending의 기존 exact cause 해제 근거만 사용한다. `wait_seq`, ticket/front 신원, 실행 nonce와 actor 세대가 일치할 때 기존 disarm을 호출한다. RootRecoveryHeld는 원래 retirement의 해제를 관측한다. 새 recheck가 기존 due나 attempts를 소비하거나 닫기 권한을 새로 얻는 경로는 없다.

#7583 HerdrCoreHost도 동일한 호스트 값 계약을 사용한다. `hc events`와 connect의 현재 snapshot이 준비도·working을 제공하고, 실제 제출 경계에서 기존 `send --if idle|working`의 수락·조건 불일치·불확실을 해석한다. interrupt는 기존 host effect 경계에 두고, reconnect 때 이전 event sequence의 준비도를 폐기한다. 수락이 불확실하면 기존 head/receipt를 정산한다. scheduler에는 초안, composer, 화면 watch가 필요하지 않다. 이 기준 HEAD에는 구현이 없으므로 boot·reconnect 계약은 #7583 설계 §11에 있다. [Herdr Core와 F4](https://github.com/itismyfield/AgentDesk/blob/e6d6e69af38e74ce4b69b00d2ae051ab514ce6a6/docs/design/i7583-session-host.design.md#L572-L581)

### 보류 부작용의 한 번 경계

같은 원본의 기존 routing identity와 host/actor 세대에 최근 typed hold reason을 연결한다. 오류 문자열의 경로·nonce·시각·상세 문구 변화는 reason에 포함하지 않는다. A→B→A 또는 원본 세대 변경은 새 보류로 처리한다. 단순 재판정은 grant stage, 동일 로그·안내 후보, marker, watch arm, retry count, durable hold commit을 반복하지 않는다. 기존 ticket의 영속 notice claim과 outbox dedupe를 사용한다. 사용자 notice 실패의 정산은 기존 영속 의무 경계에 맡긴다. 로그용 메모리는 프로세스 재시작에서 새로 시작한다.

TLC의 초 단위는 스케줄링, mailbox와 실제 transport 지연을 추상화한다. 현재 warm readiness는 오래 기다릴 수 있다(`src/services/claude_tui/hosting/warm_followup.rs:248-334`). 따라서 읽기 경계를 짧게 하고 host 준비도가 관측되는 시각과 실제 완료 시각을 각각 시험한다. 명세가 보여 주는 것은 최대 10초 간격의 재판정과 eventual delivery다. 무제한 transport/actor 지연이나 화면에만 드러나는 변화를 포함한 10초 완료 보장은 잔여 한계다.

- 경계 시각. monotonic recheck와 실제 due 각각 직전·동시·직후에 조건 변경과 wake를 배치해 정확히 한 권리만 소비하는지 본다.
- 동시성. cancel/reopen/새 epoch와 timer/old watch를 경합시켜 exact owner·watch key와 한 lane을 검증한다.

- 실행 가능한 가드. spy로 반복 로그, notice, PG writer, writer safety guard, screen probe 호출을 관측한다.
- 잘못된 0/PASS. 선택 수, RED 실패 이름과 exit, GREEN 및 mutation 결과를 기록한다. E-68 known-gap/skip은 미통과다.
